# LMA 产品定位与路线图

产品定位、能力优先级、成功标准和最终原则。**这里是方向，不是实施任务**：开始任何一项之前需要用户确认范围；现行业务规则见 [产品规则](rules.md)，未完成工作见 [状态与待办](../status.md)。

**产品名称：LMA（Landslide Monitoring Agent）**
**产品定位：面向滑坡连续监测业务的智能调查与分析助手**

------

# 1. 产品目标

LMA 不建设新的完整监测平台，而是在已有北斗/GNSS 监测平台之上，通过大语言模型 Agent 自动组织数据查询、趋势分析、多站对比、气象关联以及后续调查步骤，帮助监测人员快速理解监测数据中发生了什么，并发现值得进一步核查的变化。

系统核心目标不是替代专业人员完成最终灾害判定，而是降低连续监测数据调查的人工成本，提高：

- 缓慢形变发现能力；
- 异常复核效率；
- 多站点对比效率；
- 数据质量问题识别能力；
- 多源证据组织能力；
- 日常巡检的一致性；
- 分析过程的可追溯性。

------

# 2. 产品定位

LMA 定位为：

> **面向滑坡连续监测场景，以 GNSS/北斗位移数据为核心，结合气象、空间地形和后续地质资料进行多源调查的 LLM Agent。**

系统主要回答：

> 当前监测点发生了什么变化？
> 这种变化是否持续？
> 与过去相比是否异常？
> 与同组其他监测点相比是否具有局部性？
> 当前是否存在加速迹象？
> 数据是否可靠？
> 是否存在需要人工进一步调查的线索？

系统可以基于已有证据进行审慎的滑坡相关分析，例如：

- 某点存在长期持续位移；
- 当前变化更符合缓慢变化而非短时跳变；
- 近期变化速率有所增加或降低；
- 该点变化明显区别于同组监测点；
- 某次降雨与位移变化在时间上接近；
- 当地坡向与位移方向具有一定一致性；
- 当前现象可能与坡体缓慢变形有关。

但这类内容必须明确属于**分析推断**，不得与直接观测事实混写。

------

# 3. 数据边界

现场只有北斗/GNSS 监测站，不增加新的传感器。需要其他数据时优先使用可公开获取的来源（当前天气与地形来自 Open-Meteo，地质来自 Macrostrat），并标明来源、分辨率和时效，不写成现场实测。

------

# 4. 当前痛点

从现有实现、[状态与待办](../status.md)和 [2026-11-17 检查报告](../reviews/session-health-2026-11-17.md)归纳。标“待确认”的需要用真实使用核实。

| 痛点 | 现象与依据 | 对应方向 |
| --- | --- | --- |
| 等待长，完成了不知道 | 一次调查常需数十秒以上，超过 30 秒界面提示可先离开；调查在后台继续，但离开后没有完成提醒，只能回到会话查看 | 调查完成提醒 |
| 数据缺了哪部分说不清 | 天气、地形因网络失败时，手机首屏被失败说明占满，“数据服务”的说法没点明是天气；用户不知道缺了什么、该不该重试 | 按数据类型说明缺失与重试 |
| 巡检线索到调查要手动接 | 今日页理由文字多而杂（巡检原型由此而来）；发起调查要手动复述线索，处理到哪一步看不出 | 巡检到调查的闭环 |
| 看不到分组整体态势 | “多项目”即平台分组，但没有一屏看全组的状态、位移方向和数据新鲜度；平台自带的离线、告警、故障状态没有在测点列表展示 | 分组概览 |
| 一个测点的来龙去脉分散 | 一问一会话；同一测点的巡检线索、历次结论和对话分散在今日、测点和记录三处，难回答“从什么时候开始关注、做过哪些判断” | 测点档案 |
| 测点叫法与平台名不一致 | 用户说“scwm4号”，平台名是 SCWM-04；大小写与编号补零已处理，口头简称和旧名仍可能找不到 | 测点别名 |
| 核对数字费力 | 正文数字由模型撰写，服务端数值在相邻卡片中，靠人逐个对照 | 正文数值对照提示 |
| 交付物只有文字 | 只能导出 Markdown，汇报和存档要另外截图整理 | 可打印的调查材料 |
| 调查被中断要重来（待确认） | 部署重启会把进行中的调查标为已中断；是否能一键用原问题重新运行需核实 | 中断与失败后一键重跑 |

------

# 5. 能力优先级

后续开发以真实使用体验和业务流程为主：让监测人员从“发现要看的点”到“查清楚、留下可交付的材料”更顺。界面改动一次做一项，先看效果再继续；已有的回答呈现与依据卡片保持不变（见 [0010](../decisions/0010-keep-answer-presentation.md)）。

## P0：当前核心能力

必须稳定完成：

- LangGraph 多轮 Agent；
- 监测点/分组查询；
- GNSS 数据查询；
- 固定时刻长期趋势分析；
- 小时级细节分析；
- 数据完整性检查；
- 固定参考坐标累计位移；
- 数值特征与台阶识别；
- 同组对比；
- 天气查询；
- 综合调查回复；
- 会话流式管理；
- 按需核查依据。

已实现的双窗口分析、地图与位移矢量、DEM 坡度坡向、手动巡检、结论登记见 [当前架构](../architecture.md)。

## P1：近期重点

### 可打印的调查材料

现在只能把回答导出为 Markdown，图表和依据只留下文字目录。增加一份可直接打印或另存 PDF 的调查材料，用于汇报、存档和交给专家复核：

- 调查结论与正文章节，事实、分析与推断的分层保持不变；
- 正文引用的位移曲线、降雨色块和测点地图以静态图嵌入，与对话中的卡片同源，不重新取数；
- 每条依据写明测点、时间窗、参考基准、缺测情况、数据来源及限制；
- 标明**数据截止时间**（每条依据的最新观测时刻、缺测只统计到当前的说明）与材料生成时间，区分“数据最新到哪里”和“什么时候生成”；
- 附各测点登记的调查状态与适用时间窗；
- A4 版式，深色主题下打印仍为浅色；Markdown 导出保留。

### 降雨与位移关联

- 测点页时间轴叠加日降雨，与位移、缺测、台阶同轴查看（需要不经模型的降雨读取入口，并确认对天气服务的请求量）。
- 前期累计降雨、降雨后的滞后响应、降雨前后速率对比由数据层统一计算，作为可引用的依据卡片；模型只负责解释，相同数据重复分析时数值一致。
- 只表达时间上的接近与先后，不写降雨导致滑坡（见 [产品规则](rules.md) 第 11 节）。

### 巡检到调查的闭环

- 今日页的建议调查测点可一键发起针对该测点的调查，初筛线索随消息作为上下文，不必手动复述。
- 每个关注测点显示处理进度：未处理、调查中、已登记结论，以及结论与本次初筛是否对应同一时间窗，避免同一线索重复调查或遗漏。
- 巡检原型的全部/按组/单站巡检与视觉初判，按试用反馈决定是否并入今日页。

### 调查完成提醒与失败恢复

- 调查在后台完成时，浏览器标签标题与系统通知（用户授权后）提示，会话列表标出“进行中”和“已完成未读”。
- 依据缺失按数据类型说明，例如“天气：历史已取得，当日预报未取得”，详细原因按需展开；单项可重试，不重跑整轮调查。
- 调查因中断或失败结束时，可一键用原问题重新运行。

### 分组概览

- 每个分组一屏：地图上所有测点按初筛或调查状态着色，移动站画近期位移方向；旁边列表给最新上报时间、缺测、平台在线状态和最近结论。
- 从概览直接进入测点页或对整组发起巡检、提问。
- 只读平台与已有巡检、结论数据，不调用模型。

### 测点页补全

- 显示最新上报时间与离线提示，曲线上标出数据截止位置。
- 同组对比以灰线作背景，与依据卡片一致。
- 时间窗口除 7/30/90 天外可自定义范围。

## P2：后续增强

- **周报、月报**：从巡检记录与结论登记生成，复用调查材料的版式与依据说明；不在巡检后自动生成简报。
- **人工事件登记**：在测点页登记设备更换、迁站、基准站变更、平台维护和现场巡查，曲线上标注；调查时作为上下文，把原因已知的跳变与未解释变化分开。
- **记录检索与对比**：记录页按测点、调查状态和时间筛选，同一测点前后两次结论并排对照，看变化从何时开始。
- **定时巡检与提醒**：初筛用真实数据校准后再决定。
- **测点档案**：按时间顺序汇总一个测点的巡检线索、调查结论、人工事件和相关会话，回答“从什么时候开始关注、判断怎样变化”；只汇总已有记录，不生成新结论。
- **测点别名**：为测点登记常用叫法与旧名，查询和推荐都能识别；有多个候选时仍请用户确认。
- **正文数值对照提示**：正文中的数值与所引依据的服务端数值明显不一致时，在句末编号旁轻提示，点开即对照；不阻断回答、不改写正文。
- **人工复核标记**：在结论上记录“已复核/有异议”及备注，用于调查材料和报告；不回写给模型（2026-11-12 已决定暂不做反馈写回，实施前需重新确认）。

------

# 6. 产品成功标准

LMA 的成功不以“模型说出了滑坡”衡量。

真正需要提高的是：

1. 是否能够正确找到相关监测数据；
2. 是否能够发现缓慢持续变化；
3. 是否能够区分局部变化与多点共模变化；
4. 是否能够识别数据质量问题；
5. 是否能够避免把单点尖峰当成持续变化；
6. 是否能够正确组织天气、地形等辅助证据；
7. 是否能够避免无证据的确定性推断；
8. 是否能够让监测人员快速知道“应该先看什么”；
9. 相同数据重复分析时，核心事实是否稳定；
10. 数据缺失和工具失败时是否能够安全降级。

------

# 7. 最终产品原则

LMA 不应成为：

> 一个看到曲线后替监测人员宣布“发生滑坡”的聊天机器人。

而应成为：

> 一个能够主动获取证据、扩展时间窗口、比较历史趋势、检查同组站点、识别数据问题、调用气象和场地资料，并将事实与推断清晰区分的滑坡监测调查 Agent。

其核心价值是：

**更早发现值得关注的变化、更快完成异常调查，并把最终专业判断需要的证据准备好。**
