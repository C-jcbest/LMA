# LMA TODO 2026-09-18：官方能力优先与工程化收敛

适用分支：`codex/complete-todo`

## 一、当前判断

当前项目整体已经采用“官方能力优先”的实现路线，不需要重新设计 Agent Runtime。

已经正确采用的能力包括：

- 主 Agent 使用 LangChain `create_agent`，不再维护自定义 ReAct/ToolNode 循环。
- 使用 `ModelRetryMiddleware`、`ToolRetryMiddleware`、`ModelCallLimitMiddleware`、`ToolCallLimitMiddleware`。
- 使用官方 `SummarizationMiddleware` 管理长上下文。
- 工具使用官方 `@tool`、Pydantic `args_schema`、`ToolMessage.status` 和 artifact。
- 上下文估算使用 LangChain 官方 token approximation。
- Agent Server 负责 Thread、Checkpoint 和 Run，不自行建立第二套会话数据库。
- 前端使用 `@langchain/react/useStream`、`useToolCalls` 和 `@langchain/langgraph-sdk Client`。
- 消息直接保留 `BaseMessage/AIMessage/HumanMessage/ToolMessage`，未重新设计消息协议。
- reasoning 展示已向官方 `contentBlocks` 收敛。
- Retry、Regenerate 已使用官方 optimistic message、checkpoint/fork 语义。
- 标题和推荐作为独立无状态 Graph，与主 Agent Run 解耦。

以下代码虽然是自定义实现，但目前不应简单视为“造轮子”：

- `retry.py`：仅定义哪些异常允许官方 RetryMiddleware 重试，本身没有实现重试循环，应保留。
- `tool_protocol.py`：负责 LMA 特有的业务错误、artifact 与展示信息边界，可以存在，但应继续缩小职责。
- `context.py`：主要用于前端展示上下文使用量，没有干涉官方 SummarizationMiddleware 的压缩决策，可以保留。

当前需要重点处理的技术债主要有：

1. DeepSeek thinking adapter 依赖 `_get_request_payload`。
2. `streamCompat.ts` 依赖 `STREAM_CONTROLLER/hydrate`。
3. Stop 后由浏览器修改 checkpoint 修复未配对 Tool Call。
4. `App.tsx` 承担过多 Run、Thread、导航、标题、推荐、错误、删除和列表同步逻辑。
5. `agent/` 同时承担 Agent Runtime、领域算法、外部服务和工具协议，后端边界开始混乱。
6. Tool artifact 尚未形成稳定、版本化的前后端契约。
7. 缺少真正浏览器 → LangGraph Server 的自动化 E2E 发布门禁。
8. 从当前代码中看不到完整用户/租户隔离；如果多人共享同一 Agent Server，这是上线前必须解决的问题。
9. 缺少统一 Trace/Run/Thread/Tool 可观测性。
10. 根目录缺少面向开发者的完整 README 和 CI workflow。

## TODO 2：评估采用官方 ToolErrorMiddleware，进一步缩小 LmaMiddleware

当前 `LmaMiddleware.awrap_tool_call()` 同时承担：

- ToolException 转换；
- 参数错误转换；
- 平台错误转换；
- transient/internal 分类；
- ToolMessage 构造；
- artifact 构造。

当前 LangChain 已提供官方 `ToolErrorMiddleware`。

调整方向：

- 通用“捕获异常 → 安全 ToolMessage”优先交给官方 middleware。
- `ToolRetryMiddleware` 继续负责 transient retry。
- LMA 只保留官方能力无法表达的部分：
  - artifact.data；
  - error.category；
  - 已取得的业务证据；
  - GNSS/Weather/Site 等领域失败语义。
- 不重复实现 retry、Tool call lifecycle 或异常调度。

不要为了完全删除自定义代码而丢失业务 artifact；目标是“官方 runtime + 极薄业务投影层”。

验收：

- 参数错误；
- 业务错误；
- 429/503；
- 内部程序错误；
- 部分成功；

全部有明确测试，且模型和 UI 都不会收到原始异常、URL、堆栈或凭据。

## TODO 3：移除“Stop 后由前端修复 Agent checkpoint”的职责

当前链路：

`stream.stop(cancel=true)`
→ `getState`
→ 扫描 AI tool_calls
→ `RemoveMessage/AIMessage`
→ `threads.updateState`
→ 私有 hydrate

这是目前项目中最明显的 Runtime 耦合点。

目标原则：

**前端负责取消 Run，不负责理解并修复 Agent 内部消息配对。**

实施步骤：

1. 使用真实 Agent Server 建立 cancel-mid-tool 最小复现。
2. 明确官方 cancel 后产生未配对 AI tool call 的具体条件。
3. 检查官方当前版本是否已经保证取消后的 checkpoint 可再次运行。
4. 若官方已解决：
   - 删除 `getIncompleteToolCallMessageUpdates()`；
   - 删除 `removeIncompleteToolCallMessages()`。
5. 若官方仍无法满足：
   - 修复行为迁移到后端 Runtime 边界；
   - 封装为单一服务端操作；
   - 浏览器不直接修改 `messages` state。
6. 禁止前端以后继续增加 checkpoint 修复规则。

验收场景：

- model streaming 中 Stop；
- 单工具执行中 Stop；
- 并行工具一半完成时 Stop；
- Stop 后刷新页面；
- Stop 后立即继续提问；
- Stop 后切换会话再返回。

所有场景均不存在 dangling tool call，也不需要 UI 理解 Agent 内部消息一致性。

## TODO 6：补齐多用户 / 租户 / Thread 所有权边界

## TODO 15：重点验证后台 Run 的 reattach

这是当前聊天应用最需要真实验证的场景之一。

场景：

A 会话 Run 正在执行  
→ 用户切到 B  
→ A 服务端继续执行  
→ 用户回到 A

期望：

- 自动恢复 A 当前消息；
- 能继续收到尚未结束的流；
- Tool Call 不重复；
- AI token 不重复；
- 不需要手工复制 stream state。

同时验证：

- 浏览器刷新；
- tab background；
- 网络断开几十秒；
- Agent Server reconnect。

优先使用 `@langchain/react` 官方 reattach 能力，不自行构建 WebSocket/SSE 重连协议。
